# ADR-0006: Redis для очередей задач и pub/sub

Дата: 2026-09-15 · Статус: принято

## Контекст

Фоновая работа значительна: синхронизация Google Диска, скачивание и обработка файлов (хеши,
антивирус, превью, извлечение текста), доставка уведомлений по каналам, сканеры дедлайнов и
напоминаний, вытеснение кеша медиа. После MVP нужен realtime (WebSocket) с fan-out событий между
процессами `api` и `worker`. Postgres не должен нести эту нагрузку — он для данных. Ресурсы под
Redis будут.

## Решение

- **Redis 7** как отдельный сервис.
- Очереди — **`hibiken/asynq`**: приоритетные очереди (`critical`, `default`, `low`), ретраи
  с backoff, отложенные задачи, периодический планировщик (cron-сканеры), `asynqmon` для
  наблюдения. Задачи — сериализованные команды (Command); идемпотентность по ключу задачи.
- Pub/sub для realtime — **Redis Pub/Sub**: `events` пишет в `group_events` (Postgres) и
  публикует в канал группы; WS-хаб в `api` подписан и рассылает клиентам. Для dev — in-process
  hub (`WS_FANOUT=inproc`).
- Кеш горячих данных (presigned URL, quick-tags, счётчики непрочитанного) — по мере
  необходимости, с TTL.

## Альтернативы

- **Очередь на Postgres (river и подобные).** Меньше инфраструктуры, транзакционная постановка
  задач. Отклонено: фоновая работа с файлами и рассылками создаёт нагрузку на БД; при заданных
  ресурсах Redis предпочтительнее.
- **Postgres LISTEN/NOTIFY для realtime.** Работает для малого масштаба, но снова грузит БД и
  ограничен размером payload.
- **RabbitMQ / NATS.** Избыточно для одного сервиса и одной команды.

## Последствия

- Плюс: Postgres обслуживает только запросы данных; очереди и realtime масштабируются
  независимо; готовый мониторинг очередей.
- Минус: ещё один сервис в compose и в бэкапах (Redis — без персистентности критичных данных:
  задачи, потерянные при рестарте, восстанавливаются сканерами по состоянию в Postgres).
