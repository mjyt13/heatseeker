# ADR-0001: Монорепозиторий

Дата: 2026-09-15 · Статус: принято

## Контекст

Проект состоит из Go-ядра, Expo-приложения, веб-клиента (позже), ИИ-сервиса (позже) и общих
пакетов (UI, типы, клиент API, i18n). Команда — 1–3 человека. Контракт API должен оставаться
синхронным между сервером и клиентами без ручной работы.

## Решение

Один репозиторий:

- `apps/api` — Go-модуль (свой `go.mod`); `apps/ai` — Python; `apps/mobile`, `apps/web`,
  `packages/*` — pnpm workspaces + Turborepo.
- OpenAPI-спека генерируется из Go и коммитится в `apps/api/openapi/`; `packages/api-client`
  генерирует из неё TypeScript-типы и клиент. Изменение API без регенерации клиента ломает
  сборку, а не прод.
- Enum'ы и матрица прав генерируются из Go в `packages/shared` — один источник правды.
- `.npmrc: node-linker=hoisted` — требование Expo в pnpm-монорепо.

## Альтернативы

- **Раздельные репозитории (фронт / бэк).** Отклонено: контракт синхронизируется руками, общие
  типы дублируются или публикуются в npm, три CI, три CLAUDE.md, изменения «эндпоинт + экран»
  требуют двух PR. Для команды такого размера разделение ничего не даёт.
- **Nx / Bazel.** Избыточно; Turborepo достаточно для кеширования и параллельного запуска.

## Последствия

- Плюс: атомарные изменения, единая конфигурация линтеров, простая навигация для ИИ-агента.
- Минус: репозиторий крупнее; Go и JS-тулинг живут рядом (Taskfile для Go, turbo для JS);
  pnpm hoisted-режим менее строгий к зависимостям.
